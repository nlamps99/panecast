# 通知补齐与提醒规则

## 离线记录

Swift relay 与 tmux relay 在电脑上保存最近 2,000 条通知或明确的任务状态事件。
文件使用原子写入和仅用户可读写的权限；普通终端输出、聊天 token 流不会写入这个日志。
事件先落盘，再广播给在线手机。重启 relay 后继续使用原来的日志世代和序号。

`inbox.sync` 参数为 `cursor`（可选）、`until_cursor`（可选）、`limit`（1–200，默认 100）。
响应为 `events`、`next_cursor`、`head_cursor`、`has_more`、`reset` 和 `retained_events`。
客户端以首个响应的 `head_cursor` 固定本轮快照边界，分页期间新收到的在线事件暂存，
旧记录应用完成后才处理更新的在线事件。这样“完成事件”不会先于对应的待回应事件而丢失。
每条记录携带 `panecast_event_id` 和 `panecast_cursor`，格式为 `日志世代:序号`。

手机在连接恢复、App 回到前台、收到新的带序号事件时同步。游标、最近 2,000 个处理过的
事件 ID 和收件箱记录一起原子保存，防止重启后重复显示已读记录。历史补齐不会逐条发出
系统提醒；同步期间真正新到的在线事件仍按提醒规则处理。

当游标落在保留范围之前，或电脑日志重建导致世代变化时，`reset:true` 明确提示存在缺口。
手机保留已有记录，并补齐电脑仍保留的内容；界面不会声称恢复了已经被清理的历史。
旧 relay 不支持这个方法时，收件箱显示升级提示，在线通知仍继续工作。

## 处理状态

完成、失败、取消或请求已解决，必须携带可匹配的 notification/task/request/turn ID。
匹配时还检查来源、线程和已有的工作区/终端信息。普通文字里的“完成”“done”不会清除待处理。
已读与处理状态独立，重复投递不会撤销用户的已读/已处理状态。明确解决后取消其稍后提醒。

统一网关长期保持已授权 cmux/Codex 来源的事件连接，和手机连接生命周期分开。
cmux 来源重连时尝试补齐来源日志，来源 ID 和原始事件 ID 一起去重；撤销来源后，历史重放
会过滤该来源的数据。Codex 的结构化审批请求和 serverRequest/resolved / turn/completed
事件用于关联待处理事项。源服务本身离线期间没有产生可恢复事件时，网关不能凭空补回。

## 提醒规则

收件箱、应用内横幅、本机通知和后台推送只接收两类事件：需要回答或审批的问题、
失败或阻塞等需要处理的问题；以及明确的任务或整轮完成。普通通知、过程进度、
工具调用结束、聊天片段、自动重试、已读/清除通知和审批已处理不触发提醒。
审批已处理和取消仍会更新已有事项的处理状态。完成事件会解决关联事项，并生成一次完成提醒。
判断优先使用结构化状态和事件类型；旧 cmux hook 只识别明确的短标题/请求提示，
不会遍历聊天内容来猜测是否完成或需要回应。

每台电脑可独立设置项目静音、只提醒需要处理的问题、免打扰时间、合并重复提醒。
“只提醒需要处理的问题”默认关闭，开启后任务完成仍保留在收件箱，但不弹出提醒。
这些规则不删除收件箱记录。重复合并按项目、终端、任务及内容分组，默认一分钟内只提醒一次。
同一任务/轮次的同一事件重复投递不会再次推送；问题和完成分别计数，避免完成提醒被前一条问题合并。
免打扰使用设置中明确显示的 IANA 时区，支持夏令时及跨午夜区间；起止时刻相同表示全天。
旅行后可以选择“使用手机当前时区”。手动安排的稍后提醒和测试通知不受免打扰规则影响。

iOS 将 `preferences` 随 APNs 注册请求提交，broker 原样转发给电脑。新版 relay 回复
`preferences_applied:true`，手机才显示后台规则已同步。旧 relay 的成功登记不等于支持规则；
界面会提示尚未确认，需要升级。本机通知和应用内提示立即使用已保存规则。

Android 继续不依赖 GMS；后台连接仍存活时使用本机通知，App 被系统停止后不能保证即时提醒，
下次连接可以补齐保留的收件箱事件。Apple 实际投递、系统通知权限和系统免打扰模式需在真机验收。

筛选由手机和 relay 同时执行。旧 relay 仍可能在 App 退出时推送普通通知，需要升级并重启
实际使用的 Swift relay 或 tmux/统一网关，才能让后台推送同步采用新规则。
