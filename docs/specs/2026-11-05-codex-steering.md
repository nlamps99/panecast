# Codex 追加输入修复

这次排查发现桌面 socket 曾由终端里的辅助 Codex 进程创建；桌面 App 并未持有它。
现在仅桌面 App 直接启动的进程会建立桥接，其他 CLI 调用正常透传。部署来源使用
`desktop_app` 和锁文件中的父进程信息核验连接，避免把独立服务当成桌面运行服务。

追加请求现在带独立的 `clientUserMessageId`。客户端先显示“正在发送”，收到 RPC
接受回执后显示“已送达”；收到具有相同 `clientId` 的用户消息时，才将待处理显示
替换成正式对话记录。模型通常在当前步骤结束后消费追加内容。

同时修复：

- 当前任务取自实时状态，不再从历史中挑出任意旧的 `inProgress` 记录。
- 历史请求过期或返回稍旧的快照时，保留随后收到的消息和完成状态。
- Codex 明确返回 `no active turn to steer` 时，把同一条输入作为下一轮提交一次。
  超时、未知结果、任务 ID 不匹配均不会自动重发；草稿保留。
- 来源临时离线时保留对话组件，避免输入框因卸载丢失草稿。
- 初始化超时会关闭失败连接，允许后续重新连接，而不是永久缓存拒绝的 Promise。

验证包含真实 Codex 二进制与本地模型替身：检查追加文字进入下一次模型 HTTP 请求、
同一会话历史记录包含对应 `clientId`、结束后再发送成功，以及中断仍针对正确任务。
该测试不调用生产模型、不改动用户业务会话。

iOS 26.5 独立模拟器的 XCTest 实测了“追加 → 已送达 → 对话文字和回复出现”，
并故意延迟旧历史响应，确认新消息和完成状态不会被覆盖。可重复运行的测试位于
`client/e2e/codex-ui/Tests/Conversations.swift`。

部署后还使用独立自检会话验证了真实环境：先通过本机网关发送并收到模型回复，再通过
手机同一公网 broker 完成发送和运行中的追加。追加消息的 `clientId` 写入历史，模型
最终回复符合追加要求。提示词仅要求返回测试标记，不调用工具或读写文件。自检会话
均归档，临时登记的本机和 broker 检查设备均已撤销。用户原会话的具体错误文本尚未提供，
因此这些验证不等于已经复现了那条会话的每一种失败条件。

电脑端修复可独立部署，手机回执与状态更新需要新客户端；现有配对继续使用。
